# 대규모 사용자 대비 파이프라인 — GPS 수집 · 통과 판정 · 알림 · 채팅 · 트래킹

> 목표: 동시 접속 10만, 하늘 위 편지 50만, 분당 통과 판정 수천만 쌍 후보를 **셀 단위 배치**로 줄이고, 알림은 **사용자별 한도**로 조절한다.
> 구현 위치: `supabase/migrations/0001_schema.sql`, `supabase/functions/*`, 클라이언트 `src/services/{location,sync,analytics}.ts`.

## 1. GPS 수집 (클라이언트 → 서버)

| 단계 | 규칙 | 이유 |
|---|---|---|
| 포그라운드 | 앱 활성 시 1회 + **2km 이동 또는 5분** 마다 1회 | 배터리·쓰기 부하 |
| 백그라운드 | `expo-task-manager` · 배터리 절약 정확도 · 2km 이동마다 | OS 제한 준수 |
| 서버 저장 | `users_private.lat/lng` + `geohash6`(≈1.2km) + `geohash4`(≈39km) | 정확 좌표는 아무도 못 읽음(RLS) |
| 친구 공개 | 50km 반경 원만(`fuzz50km`) — 서버 함수가 반환 | 젠리식 프라이버시 |
| 폭주 제어 | 사용자당 위치 쓰기 **분당 1회** 초과 시 무시(Edge Function `set-location` 에서 마지막 갱신 시각 비교) | 스팸·루프 방지 |

## 2. 통과 판정 (매 분 배치, `tick-world`)

편지 × 사용자 전수 비교는 O(N·M). 대신:

1. **편지 셀 예측**: 각 비행 편지에 대해 다음 60초 동안 지날 경로를 샘플링해 `letters.cells4[]`(geohash4 셀 목록)를 갱신. 대부분 편지는 1~3셀.
2. **셀 조인**: `users_private.geohash4 = any(letters.cells4)` 인 (사용자, 편지) 후보만 정밀 판정(대권 최소 거리 ≤ 150km).
3. **핫 셀 상한**: 한 셀에 사용자 5,000명 이상(대도시)이면 편지당 **무작위 300명**만 통과 후보로 뽑는다(누구나 잡을 기회는 유지, 부하 상한).
4. **편지당 통과 상한**: 편지 하나가 1분에 만드는 통과 이벤트 ≤ 200. 초과분은 다음 분으로.
5. **중복 방지**: `passbys(user_id, letter_id)` unique.
6. **처리 시간 상한**: 함수 실행 25초 넘으면 남은 편지는 다음 틱(커서 저장). 틱은 겹치지 않도록 `pg_cron` 잠금 키 사용.

사용자 10만 · 편지 50만 기준 후보 쌍 ≈ 편지 50만 × 셀당 평균 사용자 20 = 1,000만/분 → 정밀 판정은 후보의 5% 미만이므로 수십만 회/분. Edge Function 1개(Deno)로는 부족 → **지역 샤딩**(geohash 첫 글자 32개로 분할, 병렬 호출 8개)로 확장.

## 3. 알림 (푸시 fan-out, `push-dispatch`)

| 규칙 | 값 |
|---|---|
| 통과 푸시 사용자당 하루 상한 | 12건 (`users_private.passby_pushes_today`), 초과분은 앱 내 알림만 |
| 조용한 시간 | 현지 23:00–08:00 통과 푸시 미발송(다음 날 아침 요약 1건) |
| 우선순위 | 채팅 2 · 답장/친구 3 · 잡힘/장난 4 · 통과 5 · 시스템 7 — 큐는 우선순위 순 |
| 묶음 | 같은 사용자 30초 내 통과 3건 이상이면 "편지 3통이 지나가요" 1건으로 합침 |
| 전송 | Expo Push API 100건 배치 · 실패(DeviceNotRegistered) 시 토큰 삭제 |
| 재시도 | 5xx 1회 재시도, 이후 error 기록 |

## 4. 채팅 · 실시간

- `messages`/`notifications`/`passbys` 는 Supabase Realtime(postgres_changes)로 구독. 채널은 **사용자당 1개**(`user:{id}`), 채팅방 진입 시에만 `chat:{id}` 추가.
- 전송은 RLS 로 멤버만 insert. 트리거가 수신자 푸시 큐에 넣는다.
- 연결 수 상한(프로젝트당 동시 500~10,000)을 넘기면 통과 알림은 폴링(30초)으로 폴백 — 클라이언트가 자동 전환.

## 5. 편지 이동 계산

- 서버는 매 분 `status` 전이(도착·착륙·재부상·만료)만 하고, **위치는 저장하지 않는다**. 위치 = f(출발·도착·경로·현재 시각) 이므로 클라이언트가 매초 계산해 그린다(60fps 부담 없음).
- `trail` 은 40km 마다 1점, 최대 240점.

## 6. 트래킹 이벤트

- 비회원 포함 모든 화면/버튼/스크롤 이벤트를 클라이언트가 20건 또는 10초마다 배치 → `track-events` → `events` 테이블(anon insert 만).
- 월 파티션 + 90일 후 콜드 스토리지. 대시보드 지표: 첫 진입→편지 쓰기 전환, 가입 게이트 노출→가입, 통과 알림→잡기, 답장 가속 구매율.

## 7. 안정성

- 모든 쓰기는 Edge Function 에서 **버전 체크**(letters.status 조건부 update) 로 경쟁 방지.
- 결제는 RevenueCat 웹훅(서명 검증) + `purchases.id` unique 로 중복 지급 방지, 코인은 `coin_ledger` 에 잔액 기록.
- 장애 시: 틱 중단 → 클라이언트가 로컬 보조 판정으로 도착/통과 UX 유지, 서버 복구 후 재동기화.
